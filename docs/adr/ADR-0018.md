# ADR-0018: Multi-Model Agentic Harness, OmniRoute Three-Tier Auth, Dual-Flywheel Compounding Self-Reflection & L11..L15 Earned-Trigger Frontier Governance

## Context and Problem Statement

Operating a multi-model quantitative engineering harness across six developer runtimes (`Codex`, `Claude Code`, `Gemini CLI`, `OpenCode`, `Antigravity`, and `Orca`), Windows 11, WSL2 `Noesis-SOTA`, and public GitHub Actions introduces five recurring failure modes when left unmanaged: instruction/MCP drift across runtimes, auth collisions & rate-limit stalls, open-loop agent & strategy evolution, supply-chain exposure, and speculative frontier dependency bloat (including non-OSI licenses slipping into tracked candidate lists).

This ADR establishes the unified `L7..L9` multi-model agentic harness, `OmniRoute` three-tier authentication and routing policy, honest `L8` evaluation boundaries, supply-chain gates, and earned-trigger `L11..L15` frontier governance anchored on SOTA upstream convergence per Core Trading Philosophy (`PHILOSOPHY_COMPOUNDING_MANIFEST.json`), coordinating with [ADR-0002](ADR-0002.md) (Compounding Lanes), [ADR-0012](ADR-0012.md) (Runtime SSOT & Grand-Reset), [ADR-0022](ADR-0022.md) (AGY 2.0), [ADR-0023](ADR-0023.md) (`fnox`+`age`), and [ADR-0024](ADR-0024.md) (Executable ADR Meta-Governance).

## Decision Drivers

- **Standards-Anchored Meta-Convergence:** Ground repository governance in neutral upstream standards — Linux Foundation AAIF `AGENTS.md` and `MCP` (`mcp==1.30.0`), executable MADR 4.0 living ADRs ([ADR-0024](ADR-0024.md)), PEP 735 `[dependency-groups]` (`uv.lock`), strict SPDX OSI license compliance, and Conventional Commits.
- **Strict Execution-Hot-Path Isolation:** Keep all LLMs, agent SDKs, `dspy.GEPA`, and MCP tooling permanently off `src/tier0_sota/engine.py` and `src/tier0_sota/risk.py` (`no-llm-on-execution-hot-path`).
- **Three-Tier Auth & Zero-Downtime Routing:** Preserve native OAuth subscriptions for interactive CLIs (`zero_global_api_key_override = true`), route local automations and routine CI through `OmniRoute` (`http://127.0.0.1:20128`) with HTTP 429 auto-fallback, reserve banked `anthropic`/`openai` keys strictly for high-quality SOTA CI dispatches (zero `GEMINI_API_KEY`), and automate Orca multi-account failover.
- **Truthful Active vs Frontier Classification:** Keep active `L8` strictly limited to tools genuinely locked, sandboxed, or skill-vendored in `Z:\noesis` (`inspect-ai`, `dspy`, `gepa`, `skillevaluator`, `aideml`), moving unwired tools (`harbor`, `promptfoo`, `OpenHands`) to earned-trigger `L15` and graduating transitively active OSI packages (`clarabel` -> `L5`, `gepa` -> `L8`) out of ungraduated frontier lists.
- **SPDX OSI Firewall Enforcement:** Permanently exclude non-OSI source-available, proprietary-rule, unlicensed, or non-commercial-weight repos (`treeverse/lakeFS`, `restatedev/restate`, `Arize-ai/phoenix`, `NX-AI/tirex`, `semgrep/semgrep`, `peernagy/LOBS5`, `PriorLabs/TabPFN`).

## Considered Options

1. **Per-runtime prompt copies, custom shell hooks, global API-key overrides, and speculative frontier installs** — causes CLI OAuth lockouts, fragile hook breakage, instruction drift, and non-OSI dependency bloat.
2. **Single-vendor model setup without local proxy failover, offline safety evals, or formal frontier promotion criteria** — vulnerable to rate-limit outages and lacks deterministic regression gates.
3. **Standards-Anchored Multi-Model Harness (`AAIF AGENTS.md` + `Orca` + `OmniRoute` Three-Tier Auth + `codebase-memory-mcp` + `XERJ` + `46` SHA-locked skills) + Dual-Flywheel Self-Reflection (`Optuna`/`MLflow`/`Inspect AI`/`DSPy`/`gepa`/`Dagster`/`Orca`) + `L7..L9` Supply-Chain Gates + Earned-Trigger OSI-Clean `L11..L15` Frontier Governance (chosen)**.

## Decision Outcome

Adopt **Option 3** across `L7..L9` and `L11..L15`, extending [ADR-0001](ADR-0001.md), [ADR-0002](ADR-0002.md), [ADR-0012](ADR-0012.md), [ADR-0017](ADR-0017.md), [ADR-0022](ADR-0022.md), [ADR-0023](ADR-0023.md), and [ADR-0024](ADR-0024.md).

## Consequences

- **Positive:** Prevents OAuth lockouts and multi-runtime drift across 6 agent tools, enforces honest `L8` vs `L15` classification and SPDX OSI firewall pruning (`semgrep`, `LOBS5`, `TabPFN`), graduates already-locked `Clarabel.rs` and `gepa`, and automates Dual-Flywheel self-reflection.
- **Negative:** Requires maintaining `5/5` MCP parity, 4-tier `OmniRoute`/Orca routing health, and periodic weekly Opus reflection reviews to keep frontier triggers and `XERJ` memories current.

## Pros and Cons of the Options

### Option 1: Per-runtime prompt copies, custom hooks, global API-key overrides, speculative installs

- Good, because no shared harness contract is needed up front.
- Bad, because it breaks OAuth CLIs, drifts across runtimes, and admits non-OSI/unwired shelf-ware.

### Option 2: Single-vendor model setup without local fallback or formal frontier gating

- Good, because fewer routing components run locally.
- Bad, because single-provider rate limits stall work and frontier tool adoption becomes ad-hoc.

### Option 3: Standards-anchored harness + `OmniRoute` 3-tier auth + Dual-Flywheel + OSI-clean `L11..L15` governance

- Good, because auth, safety evals, skill locks, SPDX firewall, and frontier promotions are mechanically enforced.
- Bad, because promoting any `L11..L15` candidate requires passing the full 4-gate admission protocol and updating living ADRs ([ADR-0024](ADR-0024.md)).

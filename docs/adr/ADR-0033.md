# ADR-0033: Agent Runtime Operation: One Instruction Source, Lead and Lanes, Cross-Family Build and Review, Read-Only Reviewers by Tool Allowlist, Gate-Visible Worker Trees & Runtime Updates

## Context and Problem Statement

`noesis` is built and operated by agents running in Claude Code, Codex, Gemini CLI/Antigravity, OpenCode and oh-my-pi/pi (OMP), coordinated in Orca. The owner also names OMC (oh-my-claudecode), a Claude Code plugin, among the runtimes that work on this repository, and directs that one rule binds all of them the same way (relayed in the lead's notes of 2026-11-27, not re-checked against the session): "zero self invent custom, all form sota upstream clean resolution convergence,it is the single must enforced rule for omp,omc etc". [ADR-0012](ADR-0012.md), [ADR-0018](ADR-0018.md), [ADR-0022](ADR-0022.md) and [ADR-0025](ADR-0025.md) state how those runtimes are configured, and `main` accepts changes only through pull requests ([ADR-0032](ADR-0032.md)). Reading those statements against each runtime's own documentation and against the files on `main` at `66dedc5` (2026-11-28) showed that several describe intent, not a mechanism the runtime enforces:

1. **A reviewer's read-only status rested on a mode Claude Code can ignore.** `paper-gatekeeper.md` sets `permissionMode: plan`, but "When the main conversation is in `bypassPermissions`, `acceptEdits`, or auto mode, your subagent runs in that same mode and Claude Code ignores the `permissionMode` you set." Its `tools` line granted `mcp__codebase-memory__*`, `mcp__xerj__*` and `mcp__nautilus-engine__*`; the sub-agents page gives `mcp__github__*` in `tools` as the way to "Give the subagent every tool from one server". Those servers include write tools (`manage_adr`, `index_repository`, `delete_project`, `ingest_traces`; `xerj_brain_link`, `xerj_brain_unlink`, `xerj_autoindex_remove`, `xerj_sources`, `xerj_field_report`, `xerj_corpus_feedback`), and `disallowedTools` named only `mcp__xerj__xerj_memory_store` and `mcp__nautilus-engine__stage_semi_auto_order_preset` among them.
2. **The per-runtime gatekeeper copies carry keys their runtimes do not apply as stated.** Since #6, `.codex/agents/*.toml`, `.omp/agents/*.md` and the `opencode.json` `agent` map hold hand-kept copies of the seven `.claude/agents` roles, which `scripts/sync_manifest.py` checks for 7/7 parity.
    - **Codex:** `.codex/agents/paper-gatekeeper.toml` sets `sandbox_mode = "read-only"` and `mcp_servers.*.disabled_tools`. The Codex documentation says: "Other session settings, including `sandbox_mode`, `approval_policy`, `model_provider`, and `mcp_servers`, don't override the parent configuration when placed in a custom agent file", and "Custom agent instructions can ask an agent to avoid edits, but they don't create a separate read-only sandbox." No Codex session was started for this record, so the installed behaviour is not observed.
    - **OMP:** `isReadOnlyAgent` is true when every declared tool is in `READ_ONLY_TOOL_NAMES`, which holds for the gatekeeper's `[read, find, grep, glob, ast_grep]`. OMP's `tools` list limits built-in tools only: "Structured children still receive the required `yield` tool; MCP, extension, and custom tools remain additive." An OMP agent declared read-only therefore still reaches MCP write tools unless its parent session restricts MCP (derived from the oh-my-pi v19.2.1 source and docs, not run).
    - **OpenCode:** the gatekeeper block uses the V1 `permission` map with the V2 action names `shell` and `subagent`. The OpenCode documentation: "V1 uses different field and action names. In V2, use permissions, shell, and subagent instead of permission, bash, and task." What OpenCode 2.3.0 enforces from that block is unverified.
3. **One instruction source, hand-kept copies.** `AGENTS.md` is the repository's instruction source; section 7 lists how each runtime reads it, from that runtime's own documentation or source (Antigravity's path is unverified). Agent definitions and MCP lists, however, were copied by hand per runtime, and copies drift. `.omp/mcp.json` is byte-identical to `.mcp.json`, which OMP already reads.
4. **The project Codex config switches off the hooks feature.** `.codex/config.toml` line 10 is `hooks = false` under `[features]`, so Codex sessions that load the project config run without lifecycle hooks, the user-level Orca status hooks included, which [ADR-0022](ADR-0022.md) decided to preserve (`codex features list` reported `hooks` as `false` inside the production working tree and `true` outside it on 2026-11-27; not re-run).
5. **Worker trees were invisible to the gates that check them.** Orca created its worktrees under its default base path, not under `Z:\workspaces` as `orca.yaml`, `LLM_HARNESS_MANIFEST.json` (`orca_practice.workspaces_dir_env`) and [ADR-0012](ADR-0012.md) state, and WSL `git worktree list` marked them `prunable` (2026-11-27). `orca --help` (1.4.280) never mentions `ORCA_WORKSPACES_DIR`; it offers `--worktree-base-path` only on `orca project setup-create` and `orca project setup-update`.
6. **The Orca setup script could replace the packages WSL services import.** `scripts/bootstrap_env.sh` defaults every `/mnt/*` tree in WSL to the shared venv `~/noesis/.venv` (line 20) and runs `uv sync` into it (line 57). uv "performs "exact" syncing by default, which means it will remove any packages that are not selected for installation", and it installs the project "as editable packages". A setup run in a worker clone therefore swaps the shared venv's dependency set for the worker's lock and points `tier0_sota` at the worker's source.
7. **Lane MCP profiles were declared, never applied.** `.claude/mcp-lanes/{sim,paper,tv,gate}.mcp.json` exist and are pinned by tests, but nothing starts Claude Code with them, and lane roles reach servers outside their profiles: `gate.mcp.json` lists `codebase-memory` and `xerj`, while `paper-gatekeeper` also names `nautilus-engine` and `edgartools` tools.
8. **Runtime versions moved outside the record** (measured 2026-11-28, More Information). `orca.yaml` line 1 says "verified against Orca CLI 1.4.271" while `orca --version` prints `1.4.280`; whether Orca's own updater ran automatically is not known (its automatic updates are "off by default"). The binary inside agy's mise `1.5.3` install directory reports `1.5.17` and has an `.old` copy beside it, so it was replaced in place; what replaced it is UNVERIFIED. On Windows the Gemini CLI on `PATH` is a node-global npm install (`0.69.0`) that shadows the mise pin `0.68.0`. `AGENTS.md` names `omp 19.2.1` + `pi 1.6.1`, which holds in WSL; Windows runs `19.2.0` and `1.5.2`.
9. **The cross-model review that ran used a read-only Codex session.** As the lead session reported it for 2026-11-27 (not reproduced here): a cross-model review round ran as `codex exec --sandbox read-only -o <file>` with a brief worded as a conformance review, beside a Claude round with runnable tests; Codex had refused the first brief, which used the word "attack", through OpenAI's cybersecurity filter; and on Windows Codex's `workspace-write` sandbox could not write to `Z:`. The Windows sandbox documentation names no drive limitation.

How should the repository decide agent runtime operation so that each guarantee is carried by a mechanism the runtime documents and enforces, every runtime reads the same instructions, and those mechanisms are kept current?

## Decision Drivers

- **Mechanism over instruction:** a guarantee holds only where the runtime enforces it (tool allowlists, OS sandboxes, launch flags, project trust, git, branch rulesets). "Claude treats CLAUDE.md files and auto memory as context. They aren't enforced configuration."
- **One instruction source:** `AGENTS.md`, read by each runtime through its own documented mechanism. A per-runtime agent or rule copy exists only where a runtime cannot read the shared file, and then it is generated and checked, never hand-kept (the MCP configs are held equal by a parity check; section 7).
- **Independent review:** the model family that did not write a change reviews it.
- **Gates run where the work is:** every gate-running worker tree is readable from Windows and from WSL.
- **The production working tree changes only through merged pull requests** (owner decision in `AGENTS.md` section 1, [ADR-0032](ADR-0032.md)); keeping worker setups off the shared WSL venv is this record's own decision.
- **Upstream update paths only:** runtimes and plugins change through their own updaters or pins and are re-verified after each change, never patched in place ([ADR-0032](ADR-0032.md) section 4).
- **No new authority:** no agent role gains broker, key or live access from this decision, and `src/tier0_sota/risk.py` SHA-256 (`ad8071dcd4196c4c529c02107114ebfdda6692bc9d7c220031f1b19ea3e4d847`) is untouched.
- **Public repository:** the record publishes decisions, mechanisms and the version table; user-level permission and sandbox settings stay out of it; the version table names user-level tool pins only to record which versions run.

## Considered Options

1. **Correct each runtime statement where it stands** in ADR-0012, ADR-0018, ADR-0022 and ADR-0025, with no new record.
2. **Supersede ADR-0012, ADR-0018 and ADR-0022** with one new record covering everything they decide.
3. **One new record for agent runtime operation** that amends the runtime parts of those records, with their runtime facts corrected in place and pointing here **(chosen)**.

## Decision Outcome

Adopt **Option 3**. This record amends the runtime parts of [ADR-0012](ADR-0012.md), [ADR-0018](ADR-0018.md), [ADR-0022](ADR-0022.md) and [ADR-0025](ADR-0025.md) without superseding any of them; their other decisions (the `AGENTS.md` SSOT, OmniRoute, the L11..L15 frontier, Antigravity zero-copy skills, MCP tooling ownership) stand. Runtime facts are stated here once. Where an earlier record calls a per-runtime gatekeeper setting "enforcement", section 3 states what that runtime documents. The passages that state Codex applies the gatekeeper agent file's `sandbox_mode` or `disabled_tools` (`AGENTS.md` section 1, ADR-0018 line 101, ADR-0022 line 98, [ADR-0024](ADR-0024.md) line 135, ADR-0025 line 141; lines at `66dedc5`) and the passages that record a transport fix in that file's `mcp_servers` (ADR-0012 line 135, ADR-0018 line 192, ADR-0022 line 98, ADR-0024 line 195, ADR-0025 line 147) are marked UNVERIFIED with this record, quoting the Codex documentation. The gatekeeper strings in the manifests are not marked: `scripts/sync_manifest.py` writes the `LLM_HARNESS_MANIFEST.json` copy, which changes with the parity check in planned step 1, and the hand-kept copy in `SOTA_STARRED_AND_BEYOND_MANIFEST.json` is not changed here. The passages that count every runtime's gatekeeper copy as enforcement (among them ADR-0012 line 79) and the OpenCode and OMP passages are corrected with the change that generates or removes the copies (planned step 6).

**Built** means in place when this record lands: true on `main`, or a practice in use as stated. **Planned (step N)** refers to the ordered list under Built and Planned.

### 1. Lead and Lanes in Orca

- One lead session talks to the owner and dispatches work. Orca's orchestration commands need the running Orca app: "The CLI talks to the running Orca runtime, so `orca status --json` should succeed first."
- Each worker gets one task and one tree and reports back to the lead.
    - A worker that needs no CLI flags starts with `orca agent launch --agent <id> --worktree <selector> --surface terminal --prompt <text>`. The verb takes no free agent arguments: `--agent`, `--worktree`, `--prompt`, `--model`, `--effort`, `--surface chat|terminal`, `--retry-launch`, `--pairing-code` and `--environment`, plus the UI and output flags `--focus` and `--json` (Orca 1.4.280 `orca agent launch --help`). Without `--surface` it starts "the way a new agent tab does: as a chat when your Chat | CLI choice for the agent is Chat and the agent and host support it, otherwise as a terminal"; `--surface terminal` "always runs the agent CLI", so launches do not depend on that setting.
    - A worker that needs CLI flags (a sandbox; an MCP profile once planned step 3 lands) starts with `orca terminal create --worktree <selector> --title <name> --command "<argv>"`; how it then receives its task is not settled, because Orca 1.4.280's `orca terminal send --help` reserves that verb "For shells, dev servers, REPLs and your own pane. To message another agent, use orca orchestration send; never type into its input."
- A running workflow takes no mid-run input ("No mid-run user input", Claude Code workflows page): to change its course it is stopped, its script is edited, and it is relaunched.

### 2. Build With One Model Family, Review With the Other

- Claude Code builds: it edits, commits and opens pull requests. Codex reviews: it reads the change, runs gates and probes where its sandbox allows, and reports findings; it does not land code.
- **The review pass (in use, as the lead session reported it):** `codex exec --sandbox read-only -o <file> "<brief>"`, with the brief worded as a conformance review of the change against its records and tests. `codex exec --help` lists `-s, --sandbox <SANDBOX_MODE>` (`read-only`, `workspace-write`, `danger-full-access`) and `-o, --output-last-message <FILE>` ("Specifies file where the last message from the agent should be written") in Codex 0.172.0 (Windows) and 0.171.0 (WSL).
- **A Codex session that must write inside its tree** starts with `--sandbox workspace-write` through `orca terminal create --command`. Codex's defaults there "include no network access and write permissions limited to the active workspace", and "`<writable_root>/.git` is protected as read-only whether it appears as a directory or file", so the sandbox itself does not let the session commit or push. In the Auto preset (`--sandbox workspace-write --ask-for-approval on-request`) "Codex asks for approval to edit files outside the workspace or to run commands that require network access", and such a command runs once that request is approved. On Windows that sandbox could not write to `Z:` in the lead's 2026-11-27 run (Context, item 9); for trees on `Z:` the review pass above is the form that has run.
- No Codex session is to start with `--dangerously-bypass-approvals-and-sandbox` ("avoid `--dangerously-bypass-approvals-and-sandbox` unless you are inside a dedicated sandbox VM") or under an Orca "Yolo" preset. Orca's "Agent permissions" preset (Manual, Auto or Yolo for new sessions, where Auto covers "Claude, Claude Agent Teams, and Codex") must be Manual or Auto, and "agents with custom launch arguments remain unchanged until you replace those arguments with a preset"; that is an owner setting outside the repository, and this record does not read its current value. The lead is to check `/status` (and `/debug-config`, which prints "config layer and requirements diagnostics") in a Codex session before sending its task.
- **Project trust:** "Local `codex exec` and `codex review` runs load project configuration and project-defined MCP servers only for trusted projects, even in a writable sandbox. Pass `--trust` to save trust for this and future chats. Project-defined MCP servers can run commands outside the sandbox." `codex exec --trust` saves "trust for this project and future chats, including MCP commands outside the sandbox". Once planned step 1 has landed, each full clone is trusted on its own before a session relies on `.codex/config.toml`: Codex records trust per path (`projects.<path>.trust_level`, "Mark a project or worktree as trusted or untrusted"), and its documentation does not say that one entry covers another path. Because project MCP servers run outside the sandbox, a read-only session's guarantee covers Codex's own tools; the MCP write tools are covered only once planned step 1 lists them under `disabled_tools`.
- **Planned (step 1), after the owner's approval:** `.codex/config.toml` sets `sandbox_mode = "workspace-write"` as the default for sessions started without flags (CLI flags still win, so the launch command remains the guarantee), lists the write tools of `codebase-memory`, `xerj` and `nautilus-engine` under `mcp_servers.<id>.disabled_tools`, and leaves `[features] hooks` at its default, so Codex sessions here keep the user-level Orca status hooks and the repository ships no hooks of its own. Codex custom agent files then carry no `sandbox_mode`, `approval_policy`, `model_provider` or `mcp_servers`; the 7/7 worker-parity check in `scripts/sync_manifest.py`, its tests, the `hooks = false` passages of the earlier records and the Codex agent-file passages this record marks UNVERIFIED are re-pinned in the same pull request. Until then `hooks = false` stays, and Codex `memories` stay as set.

### 3. Reviewer Roles Are Read-Only by Tool Allowlist

- **Claude Code (Built):** a reviewer role's `tools` frontmatter is an explicit allowlist: `Read`, `Grep`, `Glob`, `SendMessage`, named read-only MCP tools and, until planned step 3, `mcp__edgartools__*`. It holds no write-capable built-in and no wildcard on `codebase-memory`, `xerj` or `nautilus-engine`. `disallowedTools` repeats eight write-capable built-ins (`Write`, `Edit`, `NotebookEdit`, `Bash`, `PowerShell`, `Monitor`, `Agent` and the legacy `MultiEdit`) and names the known write tools: "If both are set, `disallowedTools` is applied first, then `tools` is resolved against the remaining pool. A tool listed in both is removed." The other built-ins that run code, start agents, create worktrees, schedule tasks or publish off the machine (among them `Workflow`, `REPL`, `EnterWorktree`, `CronCreate`, `Artifact` and `RemoteTrigger` in the tools reference) are kept out by the `tools` allowlist alone.
- **`paper-gatekeeper.md` (Built with this record):** `tools` lists `Read`, `Grep`, `Glob`, `SendMessage`, 12 `codebase-memory` tools, 10 `xerj` tools, the nine `nautilus-engine` tools annotated `readOnlyHint=true` and `openWorldHint=false`, and `mcp__edgartools__*`. `disallowedTools` keeps its eight names, including `MultiEdit`, which the manifest check still requires, and adds `PowerShell`, `Monitor`, four `codebase-memory` and six `xerj` write tools. `permissionMode: plan` and the body stay.
- **Tool classes come from the servers themselves.** `nautilus-engine`: its MCP `ToolAnnotations` in `scripts/nautilus_mcp_server.py`. `codebase-memory-mcp` 0.12.1: its upstream `readOnlyHint` annotations. `xerj` v1.0.0-rc.104 publishes no annotations, so its classes follow its own tool descriptions:
    - `xerj_search` and `xerj_hybrid_search` only read the node, but their optional `rerank` "sends the text of the top `window` hits plus the question to an external relevance model" when the node's operator has configured a provider, so the reviewer names neither.
    - Plain-text and query-DSL search stays available through `xerj_batch_search`, which has no `rerank` argument.
    - `xerj_hub_ask` ("Local packs first, hosted second") and `xerj_hub_def` are not named either: the `xerj_corpus_feedback` description speaks of "the automatic review this server sends after xerj_hub_ask / xerj_hub_def", and that tool posts to `https://hub.xerj.org/api/corpus-feedback`. Every repository MCP config sets `XERJ_DISABLE_FEEDBACK=true`, the opt-out the same description names; the allowlist does not depend on it.
    - `mcp__edgartools__*` stays a wildcard until planned step 3. edgartools `6.4.0` (the `uv.lock` pin) publishes no MCP annotations, and its tools reach SEC EDGAR over the network: `edgar_text_search` sends its query to `https://efts.sec.gov/LATEST/search-index` (read from the installed package, not run).
- Claude Code applies `tools` to a subagent and to an agent-team teammate alike ("Claude Code limits the teammate to the tools in the definition's `tools` list."). `permissionMode: plan` stays in the file but is not relied on, and neither are the definition's `skills` for a teammate ("Claude Code doesn't apply the definition's `skills` to a teammate in either display mode.").
- Read-only covers the reviewer's own actions. It can still ask others to act: `SendMessage` is on its list, and the agent-teams page adds: "For an in-process teammate, Claude Code adds `SendMessage` to that list, and in a session that has the Task tools it adds `TaskCreate`, `TaskGet`, `TaskList`, and `TaskUpdate` too." None of those runs a shell or edits a file.
- On native Windows Claude Code has no OS sandbox ("On native Windows, Claude Code runs commands unsandboxed."), so on the Claude side the allowlist and the permission deny rules are the guarantee.
- **Other runtimes:** a read-only Codex review is a session started with `--sandbox read-only` (an agent file cannot make one); OMP's `isReadOnlyAgent` covers built-in tools, not MCP tools; what OpenCode enforces from the gatekeeper block is unverified (Context 2). None of these is counted as enforcement until a test reads the mechanism the runtime documents.

### 4. Worker Trees the Gates Can See

- Every worker tree that a lead dispatches to run gates is a full clone on `Z:` (Built), readable from Windows and from WSL (`/mnt/z`). Orca's CLI help (1.4.280) lists `--worktree-base-path` on `orca project setup-create` and `orca project setup-update` without describing it, so whether setting it (`orca project setup-update --setup <setup-id> --worktree-base-path <path>`) puts new Orca worktrees on `Z:` is UNVERIFIED until planned step 4 sets it, after the owner chooses the folder, and checks where Orca then creates a worktree. Until then Orca worktrees stay under Orca's default base path, and dispatched workers do not use them for work that runs gates. The Orca automations are outside this rule ([ADR-0032](ADR-0032.md) section 3): the three report-only ones run in the production working tree, where the end-of-day audit runs `just check`, and the weekly self-reflection automation, whose prompt runs the gates, is configured for an Orca worktree under that default base path.
- A new full clone is trusted before gates or sessions rely on its configs:
    - `mise trust <clone-path>`: mise loads `[env]` only from trusted configs, and "A config in a linked git worktree is trusted when the same path in the main checkout is trusted.", which covers linked worktrees, not separate clones.
    - a WSL `git config --global --add safe.directory /mnt/z/<clone-folder>` entry;
    - Codex project trust, once planned step 1 has put the MCP write tools under `disabled_tools` (section 2).
- The production working tree `Z:\noesis` is never a worker tree, and workers are not launched from it: Claude Code places its own worktrees, by default, "under `.claude/worktrees/<name>/` at your repository root" (a `WorktreeCreate` hook can move them; the repository ships none).
- **Planned (step 2):** Orca's setup script syncs the shared WSL venv `~/noesis/.venv` only for `/mnt/z/noesis`. Every other tree gets its own WSL venv, also when the login shell has already exported `UV_PROJECT_ENVIRONMENT` as the shared one. `uv run --no-sync`, which `just` recipes use, does not change the venv it reads. The shell-profile exports outside the repository stay as they are; a worker that changes dependencies gates them with its own venv.

### 5. Automations That Write Land Through Pull Requests

- An automation that changes tracked files runs in its own worktree on a branch from `origin/main` and lands with `gh pr create` and `gh pr merge --auto --squash` through the required checks. Which Orca automations and GitHub-side jobs run where, what each writes, and the exception for the report-only automations that still run in the production working tree are recorded in [ADR-0032](ADR-0032.md) section 3; the off-repo multi-runtime convergence loop that earlier records name (ADR-0012, ADR-0018, ADR-0024, ADR-0025) is not covered there.
- Orca automations cannot carry permission or sandbox flags ("Permission, config, prompt, and session options are rejected."). "On each fresh run, Orca starts from the host's default Arguments for that agent", so an automation's posture comes from those default Arguments (which Orca's "Agent permissions" preset sets unless the agent has custom launch arguments; derived from the settings page) and the repository configs, and an automation described as read-only is read-only only by its prompt unless it runs as a reviewer role or as a read-only Codex session.

### 6. Runtime and Plugin Maintenance as Upstream Updates

- The update mechanics (one updater and one written proof per pin class, dated holds, toolchain pin moves, fixing upstream instead of patching in place) are decided in [ADR-0032](ADR-0032.md) section 4. This section adds the agent runtimes and plugins, which the repository `mise.toml` does not pin (it pins 13 tools, among them `node`, `uv` and `prek` from the table below, and no agent runtime).
- Each runtime changes only through its own upstream path (the Update path column below). Claude Code plugins "update automatically when the marketplace they came from has auto-update turned on", which is off by default for "every other marketplace, including the community marketplace, third-party marketplaces, and local development marketplaces". ## Consequences

- **Positive:** Guarantees carried by repository files have tests, except the section 7 copy rule, whose check lands with planned step 6; launch-time guarantees are checked by hand (`/status`, `/debug-config`), and the operator settings outside the repository are required but not read here. From this record on, the Claude Code reviewer holds no write-capable built-in and no `codebase-memory`, `xerj` or `nautilus-engine` write tool, whatever mode its parent session runs in, and the reviewing family's pass is a read-only session. Each runtime's path to `AGENTS.md` is written down with its source, or marked unverified. Once the planned steps land:
    - a Codex session in a trusted tree cannot write through the MCP servers' write tools, and the hooks feature is back on;
    - gates can open every worker tree from both systems (Orca worktrees only if planned step 4 shows that the base-path setting places them on `Z:`);

    - no `.omp/agents` or `.codex/agents` copy is hand-kept (the `opencode.json` `agent` map is outside the copy rule as written);

- **Negative:** Explicit tool lists are longer than wildcards and must be revisited when a server adds tools. A writing Codex session started through `orca terminal create --command` has no settled way to receive its task (section 1), while `orca agent launch` takes it as `--prompt`. Full clones need `mise trust`, a `safe.directory` entry and, after planned step 1, Codex trust. Every runtime update costs a small pull request.
- **Stated limits:**

    - **In WSL the shared venv stays the default reader.** `just` recipes point `uv run --no-sync` at it in every tree without a `.venv/bin/python` of its own (the justfile `uv_prefix`), and in every tree when the login shell exports it, so a worker that changes dependencies gates them in WSL only with its own venv.

## Pros and Cons of the Options

### Option 1: Correct each runtime statement where it stands

- Good, because no new record is needed.
- Bad, because runtime facts stay spread over four records whose main decisions are elsewhere, so every runtime update edits all four.
- Bad, because the decisions that changed (one instruction source, who builds and who reviews, where workers live, how updates land) get no record of their own.

### Option 2: Supersede ADR-0012, ADR-0018 and ADR-0022

- Good, because one record would hold everything about agents.
- Bad, because supersession in this catalog is whole-record (`supersedes` requires the earlier record to be `superseded`), which would retire their unrelated decisions (the `AGENTS.md` SSOT, OmniRoute, frontier governance, Antigravity skills).

### Option 3: One record for agent runtime operation, earlier records amended in place

- Good, because runtime facts live in one record with its own fitness checks, and the earlier decisions stand.
- Good, because each later runtime change edits this record only.
- Bad, because readers follow a pointer from the earlier records to this one.

### Self-Invention Lesson Learned & Mechanical Upstream Gate

- **Lesson Learned:** A mode name in frontmatter, an agent-file key the runtime does not apply, a read-only label that leaves MCP tools reachable, an environment variable Orca does not document, lane files no launcher passes, and per-runtime agent copies kept by hand looked like guarantees and were not. A runtime guarantee is recorded together with the runtime's own mechanism and a test that reads it; an agent or rule copy a runtime needs is generated, never hand-kept.
- **Mechanical Upstream Gates:** the required Quality gate runs, on every pull request, `pytest -q` (which collects `tests/test_agent_runtime.py`, `tests/test_architecture_manifest.py` and `tests/test_grand_reset_kit.py`), the Inspect safety suite of `evals/tier0_inspect_eval.py`, `scripts/sync_manifest.py --check` and `zensical build --clean --strict` directly, not through `just` ([ADR-0032](ADR-0032.md)). Locally, `just manifest-check` runs `scripts/sync_manifest.py --check`, `just adr-check` adds the strict docs build and the tests of `tests/test_architecture_manifest.py` selected by `-k "adr or clean_sota_harness"`, and `just check` runs the local gate set, whose result the author quotes in the pull request body.

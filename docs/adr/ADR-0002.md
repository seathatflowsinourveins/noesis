# ADR-0002: Dual-Flywheel Compounding Learning Harness (`XERJ`, `MLflow`, `DuckDB`, `Inspect AI`, `DSPy`)

- **Status:** Accepted
- **Date:** 2026-11-25
- **Evidence Grade:** E4

## Context and Problem Statement

Both engineering sessions and quantitative research trials risk repeating solved mistakes or losing empirical backtest/paper telemetry unless insights feed back automatically into a durable, queryable memory and evaluation loop.

## Decision Drivers

- Separate synchronous execution hot paths (`NautilusTrader v2`, `risk.py`) from asynchronous LLM/RAG/eval tooling.
- Persist every research trial (`<= 2026-10-15`) and paper-farm run in structured experiment and ledger stores.
- Continuously evaluate agent prompts, tool-use discipline, and security boundaries offline.

## Considered Options

1. **Ad-hoc markdown logs and manual session summaries** — unsearchable and prone to drift.
2. **Dual-Flywheel Loop:** quantitative evidence ledger (`MLflow` + per-account `DuckDB`) paired with engineering memory/eval flywheel (`XERJ :9200` + `Inspect AI` + `DSPy`).

## Decision Outcome

Adopt Option 2. Every falsification run logs parameters, costs, CPCV/DSR/SPA/HAC metrics, and git context to `MLflow` (`:5000`), while per-account paper execution telemetry lands in isolated `DuckDB` stores. Engineering architecture lessons, failure post-mortems, and converged configurations are deduplicated into `XERJ` (`http://127.0.0.1:9200`) and gated via `Inspect AI` (`:7575`) and `DSPy` outside the execution hot path.

### Consequences

- **Positive:** Closed-loop empirical learning across both trading research and multi-agent engineering.
- **Negative:** Requires running local Docker/WSL services (`MLflow`, `XERJ`) for full telemetry persistence.
